3. ATTO 1: SMONTARE IL CLICKBAIT ("IL VIBE CODING FINISCE L'11 SETTEMBRE 2026?")
[TELEPROMPTER • STEFANO • PAROLA PER PAROLA]

«Negli ultimi mesi si è diffusa sui social e su YouTube una narrazione terrorista: "Attenzione! Con l'entrata in vigore del Cyber Resilience Act europeo, il Vibe Coding è ufficialmente morto. Se usi Cursor, Claude Code o ChatGPT per creare applicazioni, dal prossimo anno rischi sanzioni fino a 15 milioni di euro".

Facciamo subito chiarezza con i testi normativi alla mano: questa affermazione è una colossale bufala da clickbait.

Il Regolamento Europeo 2024/2847 — noto come Cyber Resilience Act (CRA) — non proibisce in nessun articolo l'utilizzo dell'intelligenza artificiale per scrivere codice. Non vieta i Large Language Model, non vieta l'autocompletamento neurale e non punisce chi programma in linguaggio naturale.

Non solo: il CRA non si applica affatto al software sviluppato per uso puramente personale, a progetti di ricerca amatoriale o a piattaforme SaaS cloud erogate come mero servizio senza componenti client installabili.

Ma allora perché tutti ne parlano con ansia? C'è un punto cruciale che la maggior parte di chi fa Vibe Coding sta ignorando completamente: il CRA regola chiunque immetta sul mercato europeo "prodotti con elementi digitali".

Se costruisci un'applicazione desktop, un'app per smartphone Android o iOS, un agente software on-premise da installare sui server di un cliente o un plugin commerciale per un gestionale, tu sei legalmente un fabbricante di software. E alla legge europea non importa minimamente se il codice lo hai digitato tu a mano alle tre di notte o se lo ha scritto Claude in tre secondi. Alla legge interessa una sola cosa: che tu sia responsabile e pienamente consapevole della sicurezza di ogni singola riga e libreria che stai consegnando a quel cliente».

4. ATTO 2: LE 2 VERE SCADENZE DEL CYBER RESILIENCE ACT (2026 vs 2027)
[TELEPROMPTER • STEFANO • PAROLA PER PAROLA]

«Molti sviluppatori fanno confusione tra le date di applicazione del regolamento. Nel calendario legislativo dell'Unione Europea ci sono due scadenze distinte che ogni professionista del software deve scolpirsi in testa:

1) Prima scadenza: 11 SETTEMBRE 2026 — Obbligo di Segnalazione Vulnerabilità Attive.
Tra meno di un anno e mezzo scatta l'obbligo formale per chiunque distribuisca software di notificare a ENISA (l'Agenzia Europea per la Cybersicurezza) e al CSIRT Nazionale (in Italia incardinato presso l'Agenzia per la Cybersicurezza Nazionale - ACN) qualsiasi vulnerabilità attivamente sfruttata nei propri prodotti, secondo una timeline serratissima: un Early Warning entro 24 ore, una notifica tecnica completa entro 72 ore e una relazione finale entro 14 giorni dalla disponibilità della patch.

2) Seconda scadenza: 11 DICEMBRE 2027 — Piena Applicazione del CRA e Marcatura CE.
Dal dicembre 2027 il software commerciale immesso nell'Unione dovrà possedere i requisiti essenziali di sicurezza by-design, la marcatura CE, il fascicolo tecnico e la disponibilità obbligatoria della SBOM (Software Bill of Materials) in formato machine-readable per tutti i componenti integrati».

6. CONFRONTO: VIBE CODING CIECO vs INGEGNERIA AI CONFORME CRA
[KO] VIBE CODING CIECO (NON CONFORME CRA)
Dipendenze Flottanti: Versioni indicate con il cappelletto ^ o tilde ~ nel package.json. Ogni installazione scarica versioni diverse non testate.
Nessuna Carta d'Identità Build: Il software ha sempre la versione 0.1.0 hardcodata per mesi, senza numero di compilazione né associazione univoca.
Git Caotico: Nessun tag crittografico, commit anonimi, impossibile ricostruire quale sorgente esatta ha generato l'eseguibile del cliente.
Nessuna Distinta Base (SBOM): Zero visibilità sulle librerie transitive; le vulnerabilità zero-day rimangono invisibili fino all'attacco.
Tempo di Risposta a Incidente: Giorni o settimane di ispezione manuale disperata (violazione termine 24h CSIRT/ACN).
[OK] INGEGNERIA AI CONFORME CRA (APPROCCIO PRO)
Lockfile & SemVer Rigido: Dipendenze bloccate bit-per-bit (package-lock.json) con versioni esatte e verificate crittograficamente.
BUILD_INFO.json Integrato: Ogni singola release include metadati automatici: versione, numero di build, commit Git, branch e data UTC.
Git Tag Annotati & Firmati: Ogni build di produzione corrisponde a un tag Git immutabile (es. v1.0.1+build.20261102.1042).
SBOM CycloneDX 1.5 Machine-Readable: Distinta base completa esportata in formato standard europeo con identificatori unici purl.
Radar Istantaneo Sub-Secondo: Comando CLI aziendale che interroga tutti i progetti in 50 millisecondi ed evidenzia librerie vulnerabili.
PRINCIPIO ARCHITETTURALE YAGNI APPLICATO ALLA SICUREZZA: Più librerie terze installi per pigrizia, più allarghi la superficie d'attacco e gli oneri legali del CRA. La prima linea di difesa dell'ingegnere AI è la Standard Library First: usare le API native della piattaforma anziché aggiungere micro-pacchetti per compiti banali.

STEP A • IL FILE D'IDENTITÀ DELLA BUILD (BUILD_INFO.json)
Ogni prodotto software distribuito deve incorporare un descrittore univoco generato automaticamente durante il processo di build:
// Percorso: /public/BUILD_INFO.json oppure embedded nell'eseguibile client { "appName": "Piattaforma-Lavoro-Condivisa", "version": "1.0.1", "buildNumber": 1042, "fullBuildId": "1.0.1+build.20261102.1042", "gitCommit": "9f8a2b3c4d5e", "gitBranch": "main", "builtAt": "2026-11-02T10:15:00Z", "craCompliance": { "regulation": "EU CRA 2024/2847", "sbomFormat": "CycloneDX-1.5", "securityContact": "security@mark2.cloud", "csirtReportingReady": true } }
STEP B • LA DISTINTA BASE DIGITALE (sbom.cdx.json CYCLONEDX 1.5)
La SBOM standard europea registra ogni pacchetto con il suo identificatore globale purl (Package URL), versione esatta e hash crittografico:
// Estratto da: /sbom.cdx.json (Standard CycloneDX 1.5 approvato da ENISA) { "bomFormat": "CycloneDX", "specVersion": "1.5", "metadata": { "timestamp": "2026-11-02T10:15:00Z", "component": { "name": "piattaforma-condivisa", "version": "1.0.1", "type": "application" } }, "components": [ { "name": "next", "version": "15.5.23", "purl": "pkg:npm/next@15.5.23", "hashes": [{ "alg": "SHA-256", "content": "a7b8c9d0e1f2..." }] } ] }
STEP C • IL RADAR AZIENDALE CVE ISTANTANEO (CLI SCANNER IN 50ms)

# ============================================================================== # SYSTEM PROMPT: EU CRA COMPLIANCE & SOFTWARE SUPPLY CHAIN GUARDRAILS # ============================================================================== [RUOLO] Sei un Senior Software Security Architect specializzato in DevSecOps, conformità normativa europea (EU Cyber Resilience Act UE 2024/2847) e protezione della Software Supply Chain. [CONTESTO] Stai scrivendo codice per applicazioni commerciali soggette agli obblighi di sicurezza by-design e rendicontazione delle vulnerabilità alle autorità europee (ENISA / CSIRT ACN). [DIRETTIVE TASSATIVE DI SVILUPPO (COMPITO)] 1. STANDARD LIBRARY FIRST (REGOLA YAGNI SUPPLY CHAIN): È severamente vietato installare nuovi pacchetti npm o librerie terze se la funzionalità può essere realizzata con costrutti nativi del linguaggio o della piattaforma (es. crypto nativo per hash/UUID, fetch standard per HTTP, structuredClone per deep copy). Ogni nuova libreria aggiunge debito normativo e superficie d'attacco CRA. 2. DIPENDENZE CRITTOGRAFICAMENTE BLOCCATE: Non generare mai comandi npm install con versioni flottanti o indefinite. CARTA D'IDENTITÀ DELLA BUILD (BUILD_INFO.json): Qualsiasi processo di build o packaging deve generare o aggiornare il file descrittore con versione SemVer reale, buildNumber progressivo e identificatore Git immutabile. 4. GENERICITÀ ZERO-DAY & ISOLAMENTO: Tutti gli input esterni devono essere validati all'ingresso tramite schemi tipizzati (Zod / Typebox). È vietato l'uso di eval(), deserializzazioni insicure o query non preparate. [FORMATO DI OUTPUT RICHIESTO] Ogni volta che proponi l'aggiunta di una libreria esterna: - Giustifica esplicitamente perché la Standard Library nativa non è sufficiente. - Fornisci il comando esatto con versione esatta da aggiungere a package.json. - Indica l'impatto sulla distinta base (SBOM) del progetto.
